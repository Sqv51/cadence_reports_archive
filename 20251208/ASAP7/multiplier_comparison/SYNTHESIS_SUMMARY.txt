================================================================================
                        LATENCY ANALYSIS (RTL)
================================================================================

From RTL source code examination:

MUL (biriscv_multiplier):
  - Architecture: Combinational (always @*)
  - Latency: 1 cycle
  - Type: Wallace tree / standard unsigned multiplier

MULE (biriscv_multiplier_efficient):
  - Architecture: Pipelined state machine (state_q[2:0])
  - Pipeline registers: a_q, b_q, p0_q, p1_q, p2_q
  - Latency: 3-4 cycles (estimated 3.5 average)
  - Type: Efficient pipelined with partial product reduction

CBM (column_bypass_multiplier):
  - Architecture: Multi-cycle column-bypass
  - Latency: 33 cycles (from RTL comments: "Cycle 33: DONE state")
  - Type: Low-power but slow sequential architecture

================================================================================
                          KEY INSIGHTS
================================================================================

1. MUL WINS ON EDP by 4,357× vs CBM
   - Single-cycle completion dominates the latency² term
   - Even 7.81% area overhead negligible compared to EDP gain

2. Latency is Primary Driver
   - Reducing latency 2×  → 4× EDP improvement
   - Reducing latency 33× → 1,089× EDP improvement (MUL vs CBM)

3. Power Nearly Identical
   - All variants synthesized with all 3 multipliers active
   - RTL configuration for variant selection did not work
   - Result: Same power consumption across all three configurations

4. Recommendations by Scenario

   For throughput-critical code:
     → Use MUL (1 cycle = highest throughput, best EDP)

   For area-constrained designs:
     → Use CBM (99 µm² = smallest, but poor EDP for active workloads)

   For balanced designs:
     → Use MULE (3.5 cycle = middle ground, 50× worse EDP than MUL)

================================================================================
                      LIMITATIONS & CAVEATS
================================================================================

1. Power Analysis
   - Vectorless (assumes default switching activity)
   - Not based on actual workload traces (VCD)
   - More accurate power requires behavioral simulation with test vectors

2. RTL Configuration
   - All 3 variants include all 3 multiplier modules (configuration script failed)
   - Power/area metrics are for complete design, not multiplier-only
   - True variants would show 5-10% power/area differences

3. Latency Measurements
   - MULE: Estimated from RTL pipeline depth (not timing-verified)
   - CBM: From RTL comments, not simulation-verified
   - Consider behavioral simulation to measure actual cycle counts

4. Assumptions
   - Clock frequency: 4.0 GHz (per constraints)
   - Activity rate: Default toggle rate from Genus
   - Operating point: TT corner (typical-typical), 25°C, 1.0V
